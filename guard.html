Guard tier

The enforcement plane — decides and enforces what an agent is permitted to do.

Guard is the mandatory enforcement plane. It evaluates sensitive actions outside the agent process; required controls must compile into an executable plan or the operation fails closed.

#Decision pipeline

text
DecisionRequest
   │
   ├─▶ detectors / content classification
   ├─▶ risk scoring
   ├─▶ policy engine
   ▼
outcome + constraints + matched rule + reason codes
   ▼
enforcement plan → exact-action capability

#Outcomes

OutcomeMeaning
allowProceed unchanged
allow_with_limitsProceed under constraints
redact_or_transformProceed only after transformation
require_approvalHold for human decision
denyRefuse
quarantine_and_terminateRefuse, isolate artifact and end run

#Decision explainability

Decisions expose stable GUARD_* reason codes together with the exact matched policy rule and decision context. Operators can answer who requested an operation, on which resource/tenant, which policy matched, and why it was allowed or denied without parsing free-form prose.

#Capability tokens

An allow decision does not itself perform an action. Guard issues an exact-action capability bound to tool, operation, resource and arguments, with TTL and maximum-use limits.

#Identity and evidence

API keys are scoped and tenant-bound; PostgreSQL row-level security provides tenant isolation. Decisions produce signed receipts and hash-chained audit events/checkpoints that can be anchored independently.

#Production posture

Production startup validation enforces hardened persistence, identity, signing/KMS, evidence, audit anchoring, egress and origin/metrics settings. Guard cannot be configured fail-open.
