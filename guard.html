Guard tier

The enforcement plane — decides and enforces what an agent is permitted to do.

The Guard tier sits outside the agent process and evaluates every sensitive action before it reaches a provider, tool, data source, artifact store, or another agent. Required controls must compile into an executable enforcement plan or the operation fails closed.

#Decision pipeline

text
DecisionRequest
   │
   ├─▶ detectors ──────▶ findings (category, severity, confidence)
   │                        │
   ├─▶ content classifier ──┤   observed data classes
   │                        ▼
   ├─▶ risk scoring ─────▶ risk 0–100
   │                        │
   └─▶ policy engine ───────┴─▶ outcome + constraints
                                     │
                                     ▼
                            enforcement plan → capability token

#Outcomes

| Outcome | Meaning | | --- | --- | | allow | Proceed unchanged. | | allow_with_limits | Proceed under constraints. | | redact_or_transform | Proceed only after transformation. | | require_approval | Hold for a human decision. | | deny | Refuse. | | quarantine_and_terminate | Refuse, isolate the artifact, and end the run. |

#Detectors

Stable finding categories include prompt injection, data exfiltration, secret exposure, undeclared sensitive content, control evasion, instruction drift, material misrepresentation, fabricated completion, scope violations, disallowed tools, dangerous commands, and excessive delegation depth.

#Capability tokens

An allowed decision does not itself perform the action. Guard issues an exact-action capability token bound to the tool, operation, resource and arguments, with a TTL and maximum use count. A token obtained for one action cannot be replayed against another.

#Identity and access

  • Tenants isolate data with PostgreSQL row-level security.
  • API keys are scoped and can be bound to an immutable agent manifest, workload, instance and principal.
  • Workload identity can be provided through trusted SPIFFE assertions from a mutually authenticated proxy.

#Evidence

Every decision produces a signed receipt and events are written to a hash-chained audit log with periodic checkpoints. Checkpoints can be anchored to independently administered external destinations.

#Worker roles

Guard separates control-plane, dispatcher, lifecycle, anchor, migration, and maintenance runtime roles so durable work can scale independently.

#Production posture

Production validation refuses to start without the configured hardening requirements: PostgreSQL/TLS, mTLS, non-exportable signing, external KMS, durable evidence storage, independent audit anchoring, controlled egress, and workload identity.
